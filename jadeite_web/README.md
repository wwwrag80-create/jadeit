# جاديت ERP — النسخة السحابية (Flutter Web + Supabase + PWA)

إعادة بناء نظام إدارة مصانع الذهب كتطبيق ويب مركزي متعدد المستأجرين، يُثبَّت على سطح المكتب كبرنامج (PWA)، ويعتمد كلياً على Supabase بدل قواعد SQLite المحلية.

> 📋 **تقرير المراجعة الشاملة وكل الإصلاحات: [`REVIEW_AR.md`](REVIEW_AR.md)** — ابدأ منه،
> وفيه إجراءات عاجلة مطلوبة منك (إلغاء المفتاح السري المكشوف).

## ٢) التشغيل خطوة بخطوة

### أ. قاعدة البيانات — ثلاثة ملفات فقط

> 📘 **الدليل التفصيلي خطوة بخطوة في `SETUP_AR.md`** — اتبعه إن كانت هذه أول مرة أو ظهر أي خطأ.

في Supabase → SQL Editor:

| # | الملف | متى |
|---|---|---|
| ١ | `00_repair_auth.sql` | عند ظهور خطأ 500 `Database error querying schema` (وأيضاً وقائياً) |
| ٢ | `INSTALL_ALL.sql` | **دائماً** — يجمع كل المخطط والصلاحيات والدوال بالترتيب الصحيح |
| ٣ | `01_create_admin.sql` | بعد إنشاء المستخدم في Authentication (ضع بريدك داخل الملف) |

الملفات المرقّمة `01_schema` … `14_security_hardening` هي **المصدر**، و`INSTALL_ALL.sql`
يُولَّد منها آلياً — لا تعدّله يدوياً، بل عدّل الملف المرقّم ثم:

```bash
python3 tools/build_install_all.py
```

> عند إنشاء المستخدم من Authentication → Users، **فعّل `Auto Confirm User`** وإلا ستحصل على
> `Invalid login credentials` مهما كانت كلمة المرور صحيحة.

### ب. التطبيق

```bash
flutter pub get
flutter run -d chrome --dart-define=SUPABASE_URL=... --dart-define=SUPABASE_ANON_KEY=...
```

المفاتيح تُمرَّر عبر `--dart-define` ولا تُكتب داخل الكود (راجع `lib/core/config/supabase_config.dart`).

> ⚠️ مهم: لا تضع **service_role key** في تطبيق Flutter إطلاقاً. النسخة المبنية تُسلَّم للعملاء، والمفتاح السري يتخطى كل سياسات الحماية. كل صلاحيات المدير في هذا التصميم تأتي من دوره في `app_users` + سياسات RLS، لا من مفتاح سري.

### ج. البناء والنشر

```bash
flutter build web --release --wasm
```

انشر مجلد `build/web` على أي استضافة ثابتة (Supabase Hosting / Netlify / Vercel / Cloudflare Pages). يجب أن يكون النطاق **HTTPS** حتى يعمل التثبيت كبرنامج.

### د. الخط العربي
خطا `Cairo-Regular.ttf` و`Cairo-Bold.ttf` موجودان في `assets/fonts/` (رخصة SIL OFL في
`assets/fonts/OFL.txt`). الخط مستخدم في الواجهة **وفي ملفات PDF** معاً — بدونه يفشل البناء.

## ٣) نظام تعدد المستأجرين وانتحال الشخصية

- كل جدول يحمل `tenant_id`، وكل سياسة RLS تتحقق منه.
- العميل يرى بياناته فقط — العزل مفروض في **قاعدة البيانات** لا في الواجهة، فحتى لو تلاعب أحد بالتطبيق لن يصل لبيانات غيره.
- المدير (`role = 'admin'`) يمر عبر سياسات تمنحه وصولاً كاملاً.
- في لوحة الإدارة، الضغط على اسم عميل يغيّر `activeTenantId` في `SessionController`، فينتقل التطبيق فوراً لواجهة ذلك العميل بنفس ما يراه هو، مع شريط تنبيه دائم وزر رجوع.

## ٤) قفل التعديل
`tenants.can_edit = false` يمنع **تعديل** الحركات المسجّلة فقط (بما فيه تعديل فاتورة مرحّلة).
التسجيل الجديد والحذف يبقيان متاحين — والقيد مفروض في قاعدة البيانات (سياسة `UPDATE` في RLS
ودالة `post_transactions_batch`)، لا في الواجهة.

## ٤-ب) الفترة المحاسبية
كل حركة تُختم بالفترة المعروضة وقت تسجيلها (عمود `period`)، والتاريخ يبقى تاريخ العملية
الحقيقي — نفس سلوك برنامج سطح المكتب. فالحركة تظهر في الفترة التي سُجّلت فيها دائماً.

## ٥) الطباعة
كل الفواتير والتقارير تُولَّد لحظياً في المتصفح عبر حزمتَي `pdf` و`printing`، ولا يُخزَّن أي ملف في Supabase (توفيراً للمساحة). الاتجاه RTL وتشكيل الحروف العربية مضبوطان في `lib/printing/pdf_theme.dart`.

## ٦) ترحيل بيانات العملاء الحاليين

```bash
pip install -r migration/requirements.txt

# فحص أولاً بدون كتابة أي شيء (يعرض العدد والمجاميع والتكرارات)
python migration/migrate_sqlite_to_supabase.py --db "client_data_X.db" --tenant <TENANT_UUID> --dry-run

# ثم الترحيل الفعلي
python migration/migrate_sqlite_to_supabase.py --db "client_data_X.db" --tenant <TENANT_UUID> --execute
```

الأداة تقرأ `client_data_*.db` القديمة، تحوّل الأسماء لشجرة الحسابات الجديدة، وتحقن الحركات مع `tenant_id` الصحيح. تعمل على دفعات، وتتحقق من التكرار قبل الكتابة، وتطبع تقرير مطابقة (عدد الحركات ومجاميعها لكل شهر) لتقارنه بالنظام القديم قبل الاعتماد.

اختبارات الأداة تعمل بدون إنترنت:

```bash
python migration/test_migration.py
```

## ٧) الفحوص والاختبارات

```bash
flutter analyze && flutter test              # ١٧ اختباراً: الفواتير، النماذج، الفترات، PDF العربي
python3 tools/check_project.py               # فحص بنيوي لكود Flutter
python3 tools/check_sql.py                   # فحص سكربت التثبيت
python3 tools/build_install_all.py --check   # INSTALL_ALL مطابق للملفات المرقّمة
bash supabase/tests/run_sql_tests.sh         # على PostgreSQL محلي فقط (PGHOST/PGUSER…)
```

كل هذه الفحوص (ومعها فحوص برنامج سطح المكتب وأداة الترحيل) تعمل تلقائياً على GitHub
مع كل دفعة (`.github/workflows/ci.yml`).

الأول يتحقق من: الاستيرادات، الـ providers، دوال المستودعات، ربط الشاشات، توازن الأقواس،
وأن كل `rpc()` مستدعى من Dart له تعريف SQL و`grant`.
الثاني يتحقق من: ترتيب تعريف الدوال قبل استدعائها، الجداول قبل سياساتها، خلوّ السكربت من
`FORCE ROW LEVEL SECURITY`، وإمكانية إعادة تشغيله بأمان.

## ٨) ما هو مكتمل وما يحتاج استكمالاً

**مكتمل بالكامل:** المخطط + RLS + كل دوال الحسابات (٣١ دالة)، الجلسة وانتحال الشخصية، والشاشات الاثنتا عشرة:
المبيعات/الصادر (إدخال + عمليات + تعديل فاتورة مرحّلة) · الوارد/قبض · مراحل التصنيع · صناديق الخياس ·
الحسابات · كشف الحساب · **القيود اليومية** · **أرشيف الفواتير والبحث الموحّد** · **إقفال الصناديق** ·
**الخسائر والهالك** · الرصيد الافتتاحي · التقرير الشهري — مع الطباعة العربية وأداة الترحيل وملفات PWA.

**أُضيف:** شاشة «سجل التعديلات» للمدير (من غيّر ماذا ومتى)، ورصيد أول المدة في كشف الحساب.

**اختياري لاحقاً:** تقارير مقارنة بين الفترات.

> ✅ المشروع يُبنى فعلياً (`flutter build web --release` مع Flutter 3.27.1) و`flutter analyze`
> بلا أي ملاحظة، وسكربت SQL مُختبر على PostgreSQL 16 (تثبيت جديد + ترقية قاعدة قديمة).
